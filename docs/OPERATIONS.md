# Operational software profile

Implemented software baseline, 2026-09-11. Only synthetic sources have been
validated. This profile does not establish production certification, independent
ETSI conformance or compatibility with a real SES deployment.

## Storage and transaction boundary

The `operational` configuration replaces local lifecycle journals with the
PostgreSQL store for local 014, segmented ingestion, or 020 relay. Protocols still
use `core.Repository`; they do not issue SQL. Repositories serialize their
existing atomic lifecycle transitions into snapshots. Each transition updates:

| Schema | Contents | Access |
| --- | --- | --- |
| `kms_meta.state` | Generation/version and an allowlist of key IDs, associations, states and timestamps | Runtime and metadata observer |
| `kms_secret.state` | AES-GCM encrypted complete lifecycle snapshot | Runtime only |
| `kms_audit.events` | Append-only request intent/result and committed transition versions | Runtime INSERT; observer SELECT |

Queryable metadata excludes raw material, key fingerprints, optional protocol
extensions and reservation tokens. The encrypted snapshot also contains the
metadata needed to restore the repository. Encryption binds namespace,
generation, version and public metadata. The runtime must use a dedicated role
without ownership, superuser rights or audit UPDATE/DELETE privileges. Apply
[schema.sql](../src/internal/postgres/schema.sql) with a migration identity, then
[grants.sql](../deploy/postgres/grants.sql) with the site-managed runtime and
observer role names. Each national KMS uses its own database and credentials.

One PostgreSQL connection holds a session advisory lock for the namespace. A
version-checked transaction commits metadata, ciphertext and a transition audit
event together. Connection loss or ambiguous persistence failure permanently
disables delivery in that process. There are no automatic reconnects or retries
of consuming operations. This is a single-writer design, not active/active HA.
It still uses bounded in-memory snapshots and the existing lifetime capacities;
PostgreSQL support is not a claim of high-throughput database-native allocation.

## Configuration and provisioning

Add the following block to the existing local or segmented configuration. Paths
are examples; no credentials belong in committed configuration.

```json
{
  "operational": {
    "database": {
      "dsn_file": "/run/kms-secrets/postgres.dsn",
      "namespace": "LU-KMS-association-1",
      "checkpoint_dir": "/var/lib/kms/checkpoint",
      "wrapping_key_dir": "/run/kms-secrets/wrapping",
      "allow_local_socket": false
    },
    "crl_files": ["/run/kms-pki/local-issuer.crl.pem"],
    "upstream_crl_files": ["/run/kms-pki/provider-issuer.crl.pem"],
    "limits": {"requests_per_second": 50, "burst": 20, "max_concurrent": 4}
  }
}
```

The DSN file must be a regular, non-symlink file with mode 0600. TCP connections
require certificate and hostname verification without fallback (`sslmode=verify-full`
with the site CA). The isolated acceptance test uses an explicitly enabled private
Unix socket. It exposes no PostgreSQL TCP listener.

1. Provision the database, separate migration/runtime/observer identities, TLS
   trust and storage according to the national site's policy.
2. Run `kms --config migration.json --migrate-database` with the migration DSN.
   This action does not start a listener. Apply the grants as the migration owner.
3. Provision an external wrapping directory, mode 0700, containing `v1.key`
   (32 CSPRNG-generated bytes, mode 0600) and `active` (the text `v1`, mode 0600).
   The serving process does not generate operational wrapping keys. Use the
   site's secret provisioning service; never pass the bytes as CLI arguments.
4. Validate issued credentials as described below. Start the runtime once with
   `--initialize-state` to provision a genuinely new database namespace/checkpoint.
   Subsequent starts omit this flag. Existing namespaces cannot be silently reset.
5. Keep synthetic seeding disabled except in explicitly designated tests. A
   restarted operational namespace rejects additional startup seeding.

The `eagle` profile remains `synthetic-segmented-v1`; operational storage does not
enable an unreviewed real SES profile. The old `state_dir` remains part of the
immutable ingestion/relay association binding but is not used as the lifecycle
journal when PostgreSQL is selected.

## Enrollment, rotation and revocation

`kms-pki` generates a P-256 private key and PKCS#10 CSR for the selected URI SAN:

```sh
go run ./src/cmd/kms-pki --mode csr --out /run/kms-enrollment/generation-2 \
  --identity urn:transeuroogs:kme:lu --dns kms.lu.example
```

Submit the CSR through the site's existing CA enrollment process. This utility
does not introduce a national CA or assume an SES enrollment endpoint. The issuer
must authorize the URI SAN, DNS/IP names, validity and serverAuth/clientAuth EKUs.
Keep gateway and application credential sets separate. Validate the returned chain:

```sh
go run ./src/cmd/kms-pki --mode validate --server \
  --identity urn:transeuroogs:kme:lu --hostname kms.lu.example \
  --cert /run/kms-enrollment/generation-2/identity.crt.pem \
  --key /run/kms-enrollment/generation-2/identity.key.pem \
  --ca /run/kms-pki/ca.crt.pem --crls /run/kms-pki/issuer.crl.pem
```

Validate client credentials separately without `--server`/`--hostname`. Stage a
complete generation, stop the affected process, atomically install the reviewed
certificate/key/trust files at the configured paths and restart against the same
database/checkpoint. Never change the association or provider identity as a side
effect of certificate renewal. Certificate and trust-root changes require a
controlled restart; automatic CA enrollment/renewal is the site's responsibility.

Full signed CRLs are required for every issuer in each verified chain. Missing,
expired, wrong-issuer, delta and indirect CRLs fail closed. Replace CRL files
atomically. Go checks revocation on new TLS connections, on each incoming HTTP
request (including reused connections), and before releasing the response.
Operational outbound KMS connections do not use keep-alive, so each request
rechecks the current CRLs. The reference application constructs fresh TLS contexts
for each connection and enables OpenSSL chain CRL checking. Keep clocks synchronized.

Wrapping-key rotation uses a new private file, e.g. `v2.key`, then an atomic
replacement of `active` with `v2`. The next committed snapshot uses that key.
Retain old generations until every retained backup encrypted with them has
expired. The runtime never deletes old keys. The file-ring implementation keeps
keys outside the database, but still trusts the KMS host; an HSM/secret-service
implementation can implement `wrapping.Protector`. No HSM driver, device-specific
rotation or HSM certification is claimed. Set a rotation policy well before
2^32 AES-GCM encryptions under any one wrapping key.

## Audit and admission control

Known certificate identities have independent token buckets and a bounded global
concurrency limit. Client-supplied headers never identify callers. Unmapped peers
and revoked certificates are rejected before the repository is called.

Accepted requests append an intent before entering the handler. A bounded response
buffer holds any delivered material until the result audit is durable. An audit
failure returns 503 and burns the delivery rights already consumed. Audit rows
contain configured actors, a generated request ID, an allowlisted operation name,
phase/status and state version. Bodies, query strings and arbitrary URL paths
are excluded. TLS handshake failures and admission rejections are not a complete
security-event audit stream; integrate site monitoring separately. Database
owners can still alter audit tables: off-host immutable export remains an
operational requirement if tamper-proof retention is required.

## Backup, recovery and availability

The separate checkpoint is written **before** committing a new snapshot. It
contains the intended version and ciphertext digest. A database restored to an
older version, a mismatched generation, a missing checkpoint, or an ambiguous
write is rejected on startup. Never lower/delete the checkpoint to make startup
succeed. A rollback of both database and checkpoint by a privileged host operator
cannot be detected by this local mechanism.

For a consistent backup:

1. Quiesce applications and stop the KMS cleanly; ensure the writer has exited.
2. Back up the entire dedicated database, including all three schemas. Use a
   PostgreSQL service profile so credentials do not appear in process arguments:
   `pg_dump --dbname=service=kms_backup --format=custom --file=/secure-backup/kms.dump`.
3. Back up the matching checkpoint directory through the protected state backup
   mechanism. Preserve its permissions. Keep a latest-version checkpoint outside
   the database restore/rollback authority if that threat must be resisted.
4. Back up required wrapping-key generations through a separate secret custody
   process. Do not place them beside database backups accessible to the same reader.
5. Restart the KMS against its original live database and checkpoint.

To restore, fence/stop the old writer, restore the complete database and its
matching latest checkpoint to an isolated environment, provision the required
wrapping-key generations and use the same immutable namespace/association profile.
Start **without** `--initialize-state`. Validate consumption tombstones before
enabling applications. For a live incident, recover all acknowledged commits from
WAL/replication and retain the latest independent checkpoint; an old backup alone
must not resume key delivery. When a checkpoint is ahead of recoverable database
state, keep service stopped and reconcile with the provider/operators. There is
no unsafe "force restore" switch.

An HA design must fence the old process, retain every acknowledged commit, and
transfer a current trusted checkpoint. Automatic failover, distributed checkpoint
consensus, power-loss testing, host hardening and a site restore drill remain
deployment acceptance work. PostgreSQL's [backup documentation](https://www.postgresql.org/docs/current/backup.html)
and [locking documentation](https://www.postgresql.org/docs/current/explicit-locking.html)
describe the database mechanisms; they do not establish application key safety.

## Acceptance

```sh
make check
make demo
make relay-demo
make segmented-demo
make operational-demo APP_PYTHON=python3.14
```

The final command requires PostgreSQL binaries (`pg_config --bindir`, or set
`KMS_PG_BIN`) and Python 3.13+ with PSK-enabled OpenSSL. It creates and removes its
own private Unix-socket database cluster. Tests exercise writer exclusion,
single delivery and restart, database rollback rejection, failed commits,
metadata/secret and audit role separation, and independent application sessions
against two PostgreSQL-backed national KMSs and a synthetic provider.
